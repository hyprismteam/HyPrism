# Local Node

Автономный режим запускает `HyPrism.LocalNode` как отдельный вспомогательный процесс на loopback endpoint, например `https://h.localhost:8443`. Каждый автономный запуск игры получает собственный свободный порт из диапазона `8443`-`9999`, поэтому несколько локальных сессий могут работать одновременно. Хост отклоняет неожиданные заголовки Host, ограничивает тела запросов 2 МБ и не требует отдельно развернутый `hytale-auth-server`

## Цепочка запуска

1. `GameLauncher` выделяет изолированный endpoint Local Node, выбирает `Assets.zip` экземпляра и запускает ноду до патча и запуска игры
2. Нода создает одну временную пару ключей Ed25519 для выбранного локального профиля
3. Лаунчер получает identity и session токены через `POST /v1/sessions`
4. `ClientPatcher` направляет известные префиксы сервисов Hytale на loopback authority
5. Игра получает ограниченное доверие к сертификату через `SSL_CERT_FILE` и Java trust store PKCS#12
6. DualAuth проверяет встроенный JWK и выполняет handshake с удаленным сервером без обращения сервера к loopback-ноде игрока
7. После запуска игры лаунчер передает владение lifetime Local Node PID игрового процесса
8. Нода продолжает работать при закрытии лаунчера и самостоятельно завершается после выхода игры

Патч клиента поддерживает обычные length-prefixed строки и Linux NativeAOT frozen strings, где последний символ граничит с метаданными runtime. Замена frozen string сохраняет этот байт метаданных. Патч может переключаться между сетевым и автономным endpoint, а перед патчем другого endpoint HyPrism восстанавливает стабильную исходную копию. На macOS backup и файлы состояния патча сохраняются вне распознанного app bundle, чтобы не нарушать его подпись. Для бинарников вне app bundle эти файлы остаются рядом с бинарником и не удаляются очисткой legacy-файлов bundle

## Группы endpoint

| Группа | Маршруты |
| --- | --- |
| Готовность и ключи | `/health`, `/.well-known/jwks.json`, `/jwks.json` |
| Сессии | `/v1/sessions`, `/game-session`, `/game-session/new`, `/game-session/child`, `/game-session/refresh`, `/game-session/authorize`, `/server-join/auth-grant`, `/server-join/auth-token`, `/game-session/exchange`, `/validate`, `/server/auto-auth` |
| Управление lifetime | `/_hyprism/v1/lifecycle/attach`, `/_hyprism/v1/lifecycle/stop` с уникальным секретом процесса лаунчера |
| Управление mesh-дружбой | `/_hyprism/v1/mesh/profiles/{profileId}/identity`, `/friends`, `/invites`, `/accept`, `/complete`, `/presence` с уникальным секретом процесса лаунчера |
| Real-time gateway | авторизованный `/ws` с передачей `peer.session.open`, `peer.send` и `peer.session.close` через Mesh |
| Приглашения в мир | `/world-invite`, `/world-invites`, `/world-invites/sent`, `/world-invites/accept`, `/world-invites/reject`, `/world-invites/cancel` и `/presence/join-world` |
| Данные аккаунта | `/my-account/game-profile`, `/my-account/get-profiles`, `/my-account/get-launcher-data`, `/profile/uuid/{uuid}`, `/profile/username/{username}` |
| Аватары и косметика | `/my-account/skin`, `/my-account/cosmetics`, `/account-data/skin/{uuid}`, `/player-skins`, `/player-skins/active`, `/player-skins/{skinId}` |
| Совместимость | configs, live config, telemetry, состояния друзей, friend requests, presence и world invites из Mesh, пустые состояния party, настройки presence и пустой список серверов |

Live config использует двухэтапный контракт production-клиента. `/configs/...` возвращает social feature flags вместе с абсолютным `manifest_url`, manifest выбирает хешированный документ `feature-flags` для общей платформы, а этот документ содержит словарь вычисленных флагов. Запросы descriptor записываются в лог Local Node, чтобы можно было диагностировать переход клиента на ноль feature flags

Authorization grant и access token содержат публичный встроенный JWK, но никогда не его приватное значение `d`. Access token копирует запрошенный отпечаток сертификата в `cnf.x5t#S256`. JWKS содержит только публичные ключи активных сессий

Запросы child-session и refresh выпускают новые пары токенов с существующим ключом профиля. В `/game-session/authorize` Bearer token подтверждает сессию игрока, а identity token в теле запроса указывает на целевой сервер. Это повторяет upstream handshake одиночной игры и не позволяет принять личность сервера за сессию игрока

Identity token, authorization grant и server access token передают активные данные персонажа в строковом claim `skin`, как в upstream-сервере. Встроенный сервер читает этот claim при создании игрока, а endpoint аккаунта и скинов продолжают обслуживать редактор в меню

`/my-account/cosmetics` повторяет форму ответа `sanasol/hytale-auth-server`. Нода читает каждую категорию редактора персонажа из `Assets.zip` активного экземпляра и возвращает ID всех установленных предметов как разблокированные. Небольшой upstream-каталог совместимости используется только тогда, когда архив отсутствует или поврежден

## Хранение и доверие

Каждый автономный запуск хранит runtime-данные в `LocalNode/Sessions/<session-id>` внутри каталога данных HyPrism. Это исключает конфликт control-secret и trust bundle между одновременно работающими локальными сессиями. Локальные профили, выбранные скины и настройки presence остаются в общем файле `LocalNode/Accounts.json`, где ключом служит стабильный UUID выбранного профиля лаунчера

Центр сертификации TLS намеренно общий и хранится в `LocalNode/Certificate`. Он подписывает серверный сертификат `h.localhost`, выданный для имени хоста, а не для конкретного порта. Поэтому каждый endpoint Local Node использует одну доверенную цепочку без повторного системного запроса доверия

| Файл | Назначение |
| --- | --- |
| `Accounts.json` | общие локальные профили, скины, активный скин и настройки presence с ключом UUID профиля лаунчера |
| `accounts.lock` | кратковременная межпроцессная блокировка, которая сериализует изменения общих локальных профилей |
| `Mesh/Identities/<profile-hash>.json` | стабильная mesh-identity с ключами подписи Ed25519 и agreement X25519 одного автономного профиля |
| `Mesh/Friends.json` | ограниченный локальный граф друзей, хеши выданных приглашений и состояние replay protection |
| `Mesh/*.lock` | кратковременные межпроцессные блокировки, которые сериализуют изменения общего mesh-состояния |
| `hyprism-local-ca.pfx` | общий локальный центр сертификации и приватный ключ в `LocalNode/Certificate` |
| `hyprism-local-ca.crt` | общий публичный центр сертификации PEM в `LocalNode/Certificate` |
| `h.localhost.pfx` | общий серверный TLS-сертификат и приватный ключ, подписанные локальным центром |
| `h.localhost.crt` | общий серверный сертификат PEM, подписанный локальным центром |
| `client-ca-bundle.pem` | набор CA для игрового процесса Unix |
| `client-trust.p12` | Java trust store для JVM встроенного сервера |
| `macos-trusted-v2.crt` | копия сертификата, зарегистрированного в trust settings macOS, используется для пропуска повторного подтверждения при следующих запусках |
Серверный сертификат `h.localhost` заменяется, если он поврежден, выпущен для другого хоста, не подписан локальным центром HyPrism или будет действовать менее семи дней. Центр сертификации сохраняется десять лет, если не поврежден. Windows добавляет этот центр в root store текущего пользователя только при отсутствии его отпечатка, затем удаляет прежние самоподписанные корневые сертификаты HyPrism после установки доверия к активному центру. Серверный ключ Windows импортируется без `EphemeralKeySet`, что требуется Schannel для TLS в Kestrel, и без `PersistKeySet`, поэтому импортированный контейнер ключа освобождается вместе с сертификатом. Linux и macOS передают объединенный CA bundle игровому процессу для компонентов OpenSSL, а Java на каждой платформе получает отдельный trust store PKCS#12

При первом автономном запуске HyPrism регистрирует локальный центр сертификации в admin trust settings macOS, чтобы игровой клиент и системные TLS-потребители доверяли loopback-эндпоинту. Регистрация может показать одноразовый запрос подтверждения. Маркер `macos-trusted-v2.crt` хранит зарегистрированный центр сертификации, поэтому последующие запуски пропускают запрос, а прежняя root-запись доверия удаляется только при ротации центра. Серверный сертификат остается ограниченным хостом `h.localhost`. HyPrism проверяет всю цепочку до запуска игры. Отмена системного диалога останавливает автономный запуск с понятной ошибкой вместо ослабления проверки сертификатов

Провайдеры логирования ASP.NET отключены для вспомогательного процесса, поэтому диагностика запросов сервера не использует статический логгер HyPrism и его console stream. Лаунчер сообщает только о запуске процесса, готовности, привязке и исключительных ошибках управления. Подробные события ноды остаются в `Logs/<время-запуска>/local-node-<порт>.log`, а предыдущий файл после ротации по размеру называется `local-node-<порт>.previous.log`. Метаданные неизвестных запросов записываются в `local-node-requests-<порт>.ndjson` в той же папке. Для маршрутов авторизации записываются только method, path, response status и duration без заголовков, токенов и тел запросов

Встроенный хост автоматически получает каталог активного экземпляра игры, а также общие каталоги сертификатов, аккаунтов, mesh и логов сессии. При управляемом запуске полное значение `MeshTransportOptions` передается дочернему процессу через внутренний кодированный аргумент `--mesh-options`, поэтому пользовательские discovery targets, порты, настройки DHT и временные ограничения не заменяются значениями по умолчанию на границе процессов. При отдельном запуске `HyPrism.LocalNode` передайте `--assets-path /absolute/path/to/Assets.zip`, чтобы открыть полный каталог установленной косметики, `--certificate-directory /absolute/path/to/Certificate`, чтобы использовать уже доверенный локальный центр сертификации, и `--account-data-directory /absolute/path/to/LocalNode`, чтобы использовать локальные профили, скины, mesh-identities и дружеские связи. Параметры `--log-file /absolute/path/to/local-node.log` и `--request-journal /absolute/path/to/requests.ndjson` переопределяют два пути диагностики. Без этих параметров standalone-режим хранит оба файла в своем каталоге данных

## Основа mesh-дружбы

Каждый автономный профиль получает постоянный mesh Peer ID, производный от отдельного ключа подписи Ed25519, и отдельный agreement key X25519. Эта identity не связана с временным ключом OmniAuth одного игрового процесса, поэтому дружеские связи переживают перезапуски игры и лаунчера. Identity-файлы версии 1 сохраняют прежний Peer ID и атомарно получают agreement key при переходе на версию 2. Файлы приватной identity и состояния друзей получают права только владельца в Unix и наследуют права каталога данных приложения текущего пользователя в Windows

Ручной control API сохраняет двухэтапный pairing с передачей данных вне Mesh. Инициатор создает подписанную capability `hyprism://friend/v2/invite/` с 256 битами случайности и сроком жизни не более 24 часов. Получатель проверяет подпись, оба публичных ключа, Peer ID, время, размер и одноразовую capability, затем возвращает подписанный ответ `hyprism://friend/v2/accept/`. Инициатор завершает обмен только тогда, когда ответ соответствует активной capability, ранее созданной локально. Описанный ниже внутриигровой поток Friend ID автоматически доставляет ту же подписанную capability. Дружеские записи pairing версии 1 не имеют проверенного agreement key и требуют повторный pairing перед использованием зашифрованного транспорта

Локальное состояние ограничивает количество друзей, активных и использованных приглашений, длину отображаемого имени и размер токена. Подписанные payload приглашения и подтверждения также передают UUID профиля лаунчера, который нужен social API Hytale. Созданные до появления этого поля friendship остаются корректными для mesh-шифрования, но для появления в списке друзей Hytale их нужно создать заново. Просроченные replay-записи удаляются при изменениях, а действующие записи никогда не вытесняются ради входных данных атакующего. Маршруты управления дружбой остаются доступны только через loopback и требуют уникальный control secret процесса лаунчера. Приватный ключ подписи через них не возвращается

Подтвержденные друзья получают одинаковый 256-битный pairwise key через X25519 и привязанную к контексту конструкцию HKDF. Mesh-envelope связывает Peer ID отправителя и получателя, случайный message ID, тип сообщения, время и ограниченный payload. AES-GCM защищает конфиденциальность и целостность, а Ed25519 подтверждает отправителя. Входной pipeline использует bounded channel с одним reader, отклоняет работу до выделения памяти при заполненной очереди и хранит ограниченное replay window для каждого друга без вытеснения действующих записей

Создание автономной сессии активирует ее mesh-профиль в процессе Local Node. Нода отправляет отдельное персональное зашифрованное объявление каждому подтвержденному другу через IPv4 LAN multicast на `239.255.72.80:47831` и принимает pairwise-трафик на случайном UDP-порту. Открытый заголовок `HPD2` содержит только минутную эпоху, 128-битный friend-specific routing tag, случайный nonce и длину шифротекста. Peer ID отправителя и получателя, timestamp и transport port находятся внутри AES-GCM шифротекста, подтвержденного подписью Ed25519 отправителя

Routing tag выводится из pairwise-ключа дружбы, направления и эпохи. Local Node заранее строит ограниченный индекс тегов для текущего временного окна, поэтому неизвестный пакет отбрасывается по opaque tag до проверки подписи и расшифровки. Discovery encryption, routing и обычные message envelopes используют раздельные производные ключи. При замене discovery-цикла предыдущий производный ключевой материал очищается из памяти

Распознать и проверить объявление может только его подтвержденный друг. Объявленный endpoint остается кандидатом до получения с этого адреса корректно подписанного и зашифрованного envelope, а свежий replay с другого адреса не может заменить действующий подтвержденный endpoint

Discovery и transport datagrams проходят фиксированные ограничения размера до проверки подписи и расшифровки. Discovery-пакеты с неизвестными непрозрачными маршрутами отбрасываются до расходования bounded token bucket, поэтому персональные объявления большого списка друзей не истощают лимит друг друга на принимающей ноде. Известные маршруты и transport datagrams остаются ограниченными по исходному IP. Неизвестные пиры, устаревшие объявления, несовпадающие исходные endpoint, поврежденные frames, повторные message ID и пакеты при заполненной очереди отбрасываются. Корректный presence-envelope обновляет локальное состояние друзей, которое возвращает защищенный control route `/presence`. Другие подтвержденные сообщения попадают в отдельную ограниченную application queue. Online-состояние истекает при остановке подписанных heartbeat, а при завершении нода пытается отправить offline presence до закрытия сокетов

Вращающиеся теги не позволяют пассивному наблюдателю в LAN прочитать стабильный Peer ID или связать один тег между эпохами. Наблюдатель все еще может оценить количество и время персональных объявлений, поэтому механизм скрывает discovery identity, но не обеспечивает анонимность формы трафика

Local Node предоставляет Hytale-совместимый envelope `socket-gateway` по адресу `/ws` и принимает только действующий токен локальной сессии. Gateway преобразует `peer.session.open`, `peer.send` и `peer.session.close` в зашифрованные Mesh-сообщения `IceSignal`, сообщает о наличии живого gateway-соединения удаленного профиля, сохраняет sequence number и непрозрачный ICE payload, а затем отправляет клиенту `peer.session.opened`, `peer.message`, `peer.session.closed`, `peer.session.ack` или `peer.error`. Размеры сообщений и очередей ограничены, а открыть сессию может только подтвержденный друг, чей подписанный UUID профиля совпадает с запрошенным игроком

World invites передают непрозрачный P2P invite code хоста в зашифрованных Mesh-сообщениях `WorldInvite`. Получающая нода хранит приглашение десять минут, возвращает его через `/world-invites`, помечает друга как доступного для подключения и передает изменения received, accepted, rejected и canceled через вложенные события `gateway.notification`. Маршруты `/world-invites/accept` и `/presence/join-world` возвращают P2P invite code в форме join-response клиента. Количество приглашений и размер кода ограничены для каждого профиля, повторные datagrams обрабатываются идемпотентно, а каждое lifecycle-сообщение привязано к исходному другу и подписанным UUID обоих профилей

Pairing доступен и внутри игрового диалога, без ручного обмена invite-кодами. Каждая mesh-identity предоставляет стабильный 16-символьный Friend ID, вычисленный как усеченный Base32 fingerprint Ed25519 публичного ключа поверх доменно-разделенного хеша SHA-256. Friend ID не содержит адреса и ключей. Он возвращается как `friendId` защищенным identity control endpoint и записывается в лог Local Node при активации профиля. Ввод в диалог добавления друзей Hytale доходит до `/friend-requests/by-username`, где лаунчер нормализует похожие символы, отклоняет некорректный ввод и создает pairing-запрос

Поскольку Friend ID не содержит доступного адреса, каждый активный профиль публикует свой эфемерный UDP transport port в публичной Mainline Kademlia DHT под доменно-разделенной 160-битной темой, выведенной из собственного Friend ID. SHA-1 используется только для фиксированного размера ключа поиска DHT и не обеспечивает аутентификацию. Поиск использует стандартные bencoded запросы `get_peers` с compact node и peer значениями, а также announce token, а `announce_peer` сохраняет исходный UDP-порт через `implied_port`. Волны запросов и цели анонса упорядочиваются по XOR-расстоянию до темы. Периодический refresh повторяет обе операции для каждого активного профиля, пока включен `EnableInternetDiscovery`. Результаты публичной DHT ограничены публичными IPv4-адресами, ответ должен прийти от опрошенной ноды, а все возвращенные endpoint остаются недоверенными до успешной проверки Mesh-identity

Доставка запроса сначала отправляет ограниченный probe-datagram `HPP1` на каждый endpoint, который DHT вернула для целевого Friend ID, и на LAN discovery targets. Получатель сначала возвращает stateless HMAC cookie, привязанный к видимому исходному endpoint, и только endpoint, который повторил challenge, получает подписанный ответ identity. Полную capability `hyprism://friend/v2/invite/` получает только нода, которая вернула корректную короткоживущую PeerRecord, подписанную запрошенной identity. Purpose PeerRecord и request ID защищены ее подписью, а само приглашение подписано и привязано к Friend ID получателя. После этого получатель показывает запрос в `/friend-requests/incoming`. Punch-datagrams через endpoint из DHT позволяют обеим нодам открыть NAT mapping навстречу друг другу, а подтверждение возвращается как подписанный ответ `hyprism://friend/v2/accept/` по тому же пути с ограниченными повторами. Pairing-datagrams проходят те же ограничения размера и per-IP token bucket, что и остальные входящие пакеты, а завершение по-прежнему требует локально выданную capability и совпадение fingerprint Friend ID, поэтому результат DHT не может выдать себя за запрошенную identity

Этот транспорт пока не предоставляет долговременное mailbox-хранилище, relay-трафик, TURN для игрового трафика и гарантированный NAT traversal. Hole punching работает только для совместимых address mapping, поэтому симметричные NAT требуют проброс порта, IPv6, UPnP, VPN или будущий relay-слой. Узлы DHT узнают только тему Friend ID, анонсирующий endpoint и стандартные bencoded поля маршрутизации. Pairing probe содержит целевой Friend ID, а PeerRecord и capability до установления дружбы подписаны, но не зашифрованы, поэтому активный relay на прямом пути может увидеть UUID профиля, имя и публичные ключи identity. Весь трафик после подтверждения дружбы использует зашифрованный pairwise Mesh-канал

## Ограничения

Local Node теперь предоставляет приватный подтвержденный discovery, presence, world invites, join metadata, peer-session signaling и серверные friend requests на основе Friend ID. Discovery охватывает одну доступную IPv4 LAN и публичный rendezvous в Mainline Kademlia DHT, пока включен internet discovery. Полный lifecycle приглашения, gateway-путь, обработку DHT-пакетов и цикл pairing по Friend ID покрывают интеграционные тесты двух нод, но это пока не проверено запуском двух установленных production-клиентов Hytale за реальными NAT. Relay fallback, offline-доставка через mailbox, TURN для игрового трафика и долговременная синхронизация состояния все еще требуют следующих слоев mesh-сети

Ошибки активации Mesh и чтения его сохраненного состояния записываются в лог и приводят к пустому social-списку, но не мешают созданию автономной игровой сессии

Формы HTTP endpoint основаны на открытой поверхности совместимости `sanasol/hytale-auth-server`. Имена типов, маршруты и поля payload шлюза и world invites восстановлены из метаданных установленного pre-release клиента. Автоматические тесты покрывают локальную HTTPS-сесию, аккаунт, JWKS, обмен grant, привязку сертификата, хранение аватаров, переключение патча, зашифрованную передачу peer-session, lifecycle приглашений, встроенный цикл pairing по Friend ID и обработку DHT-пакетов `get_peers` и `announce_peer`. End-to-end проверка каждой будущей проприетарной сборки клиента Hytale все еще требует совместимую установку клиента

## Параллельные запуски

HyPrism рассматривает каждый игровой экземпляр как отдельную цель запуска. Один экземпляр нельзя запустить дважды, потому что у него общие файлы клиента и пользовательские данные, но разные каталоги экземпляров могут одновременно работать в разных режимах авторизации. Например, один экземпляр может использовать Local Node, второй кастомный сервис авторизации, а третий официальную авторизацию

Лаунчер хранит runtime-реестр процессов с PID, временем запуска процесса, экземпляром и профилем. При следующем запуске HyPrism восстанавливает только записи с живым процессом и совпадающим временем старта. Завершившиеся пока лаунчер был закрыт записи один раз сверяются, чтобы сохранить время игры и cleanup запуска, а устаревшие записи и переиспользованные PID удаляются автоматически

Для официальной авторизации намеренно действует ограничение один запущенный клиент на владельца Hytale-аккаунта. HyPrism сериализует официальную авторизацию между процессами лаунчера и отклоняет второй запуск, если в восстановленном реестре уже есть этот аккаунт
