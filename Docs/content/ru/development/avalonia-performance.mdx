# Производительность Avalonia

HyPrism использует Avalonia 12.1.1 и включает compiled bindings для всего проекта Desktop. Оптимизация производительности должна опираться на воспроизводимый trace, render-тест или измеренное изменение визуального дерева

## Текущие настройки runtime

- неактивные страницы Instances, News, Settings и Profiles создаются при первом переходе и сохраняются для следующих посещений
- бюджет начального headless-визуального дерева равен 160 потомкам, измеренный результат после отложенного создания страниц снизился с 410 до 144
- большие коллекции модов и миров используют ограниченный по высоте `ListBox` с `VirtualizingStackPanel` и cache length 1
- замена коллекций публикует одно reset-уведомление вместо отдельного уведомления на каждый элемент
- обновления прогресса загрузки объединяются до последнего ожидающего значения перед обработкой UI-диспетчером
- непрерывное пользовательское вращение использует `TopLevel.RequestAnimationFrame` и не изменяет transform, пока визуальный элемент фактически скрыт
- плавный скролл и auto-scroll средней кнопкой анимируются через `TopLevel.RequestAnimationFrame` с easing, независимым от частоты кадров, вместо фиксированного таймера 16 мс, поэтому обновления колеса следуют частоте обновления дисплея
- декодирование фонового bitmap выполняется вне UI-потока
- кэш GPU-ресурсов Skia ограничен 256 МиБ, чтобы удерживать активный фон 1920x1080 и декодированные изображения новостей без частого вытеснения
- region dirty rectangle clipping сохраняет стандартное значение Avalonia 12.1, поскольку его стоимость на CPU может снижать частоту кадров на desktop с GPU-ускорением
- Windows-рендеринг ANGLE запрашивает у DXGI high-performance адаптер и сопоставляет его с адаптером Avalonia по LUID, сохраняя программный рендеринг как fallback
- режим композиции Windows по умолчанию использует low-latency flip-model DXGI swap chain с pacing по vblank дисплея, а переменная окружения `HYPRISM_WIN32_COMPOSITION` возвращает старые режимы для диагностики со значением `winui` или `dcomp`
- сборщик мусора .NET работает в режиме SustainedLowLatency, чтобы блокирующие сборки реже прерывали анимационные кадры
- Linux-пакеты объявляют `PrefersNonDefaultGPU=true`; при прямом запуске переменные Mesa и NVIDIA PRIME добавляются только если DRM показывает несколько адаптеров, а значения пользователя или desktop environment не заменяются

## Правила коллекций и layout

Размещайте длинную прокручиваемую коллекцию в ограниченной строке `Grid`. Используйте встроенный виртуализированный `ListBox`, когда нужен выбор или поддерживаемый Avalonia 12.1 контрол. Оставляйте `ItemsControl` для небольших ограниченных групп, например категорий навигации, блоков статьи и строк участников

Не размещайте виртуализированный список в `StackPanel` вдоль оси прокрутки. Бесконечное ограничение layout отключает виртуализацию. По возможности сохраняйте стабильную высоту элементов, поскольку переменные оценки вызывают дополнительную работу layout при прокрутке

Используйте `IsVisible="False"` для неактивного содержимого. Элемент с нулевой прозрачностью продолжает участвовать в layout, рендеринге и hit testing. Отключайте hit testing у декоративных overlay и применяйте clipping, тени и пересекающуюся прозрачность только там, где они нужны дизайну

## Правила обновлений и анимаций

Формируйте и преобразуйте данные вне UI-потока, затем публикуйте готовый пакет через диспетчер. Высокочастотные источники, например прогресс загрузки, должны держать не более одного ожидающего callback диспетчера и применять последнее значение

Используйте переходы Avalonia или `TopLevel.RequestAnimationFrame` для покадрового интерфейса. Timestamp из callback синхронизирован с циклом анимации и рендеринга Avalonia. Не создавайте постоянный 16-мс `DispatcherTimer` для каждого анимированного элемента

## Процесс профилирования

1. Повторяйте одинаковый размер окна, путь навигации, объём данных и renderer при каждом запуске
2. Используйте Avalonia DevTools для проверки визуального дерева, layout, перерисовок и диагностики renderer
3. Снимайте CPU- и allocation-trace отдельно для запуска, навигации, прокрутки и прогресса загрузки
4. Сравнивайте число визуальных элементов, время UI-потока, allocations, стабильность кадров и working set до и после изменения
5. Добавляйте отдельный headless- или render-регрессионный тест для каждой сохранённой оптимизации

После изменений производительности UI запускайте набор регрессионных тестов Desktop

```bash
dotnet test Tests/HyPrism.Desktop.Tests/HyPrism.Desktop.Tests.csproj
```

Стартовый бюджет контролируется тестом `AvaloniaPerformanceTests.MainWindowInitialVisualTreeStaysWithinBudget`
