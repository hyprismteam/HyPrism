# Building

## Requirements

- .NET 10 SDK
- Git
- Node.js 22 and pnpm only when working on the documentation

## Native launcher

```bash
dotnet restore HyPrism.sln
dotnet build Sources/HyPrism.Desktop/HyPrism.Desktop.csproj
dotnet run --project Sources/HyPrism.Desktop/HyPrism.Desktop.csproj
```

## Entire solution

```bash
dotnet build HyPrism.sln
```

The solution contains `HyPrism.Core`, `HyPrism.Desktop`, `HyPrism.LocalNode`, and their test projects

## Local publishing

Release entry points and their platform assets are centralized under `Packaging/`. On Linux, the publisher creates `deb`, `rpm`, AppImage, Flatpak bundle, and `tar.xz` from one self-contained Desktop publish output. Install `rpm`, Flatpak, Flatpak Builder, and appimagetool first, then run:

```bash
./Packaging/publish-linux.sh all --output dist
```

Use a specific Linux target such as `deb`, `rpm`, `appimage`, `flatpak`, or `tar` to build only that package. On macOS, `./Packaging/publish-macos.sh dmg` creates the DMG. On Windows, `pwsh Packaging/publish-windows.ps1 all` creates ZIP, MSI, and EXE installer. Each platform workflow directly calls its corresponding entry point

The Windows publisher verifies that both `HyPrism.Desktop.exe` and `HyPrism.LocalNode.exe` exist before creating portable and installer artifacts. It installs the pinned WiX 6 tool in an isolated temporary directory and uses the matching bootstrapper extension version

The `Version` property in `Sources/HyPrism.Desktop/HyPrism.Desktop.csproj` is the only release version source. Packaging scripts evaluate it through MSBuild for assembly metadata, package metadata, and artifact names. A release tag must match `v<Version>` or the release workflow fails

## GitHub Actions

`.github/workflows/ci.yml` is the push and pull request entry point. It calls the independent test workflow and the build dispatcher. `.github/workflows/build.yml` only selects platforms, while `build-linux.yml`, `build-windows.yml`, and `build-macos.yml` own their platform packaging

The current CI artifacts are Linux x64 `deb`, `rpm`, AppImage, Flatpak bundle, and `tar.xz`, Windows x64 portable ZIP, MSI, and EXE installer, and a macOS ARM64 DMG. Release builds reuse the same platform workflows and pass the release version into artifact names

The Linux workflow retries the Flathub runtime installation when remote metadata or package downloads fail temporarily. The final failed attempt still stops the build before packaging starts. Flatpak export and bundle creation use the same `stable` branch selected by the Linux publisher

## macOS package

The macOS workflow publishes the self-contained `osx-arm64` Desktop application with the Local Node apphost beside it, builds a native `.app` bundle, applies an ad hoc signature, verifies the bundle, and creates the uploaded DMG

## Documentation

```bash
cd Docs
pnpm install --frozen-lockfile
pnpm build
```

The static site is written to `Docs/out`
