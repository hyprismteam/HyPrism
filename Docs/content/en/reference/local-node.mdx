# Local Node

Autonomous mode runs `HyPrism.LocalNode` as a dedicated companion process on a loopback endpoint such as `https://h.localhost:8443`. Each autonomous game launch receives its own free port in the `8443` to `9999` range, so multiple local sessions can run together. The node rejects unexpected Host headers, limits request bodies to 2 MB, and does not require a separately deployed `hytale-auth-server`

## Launch flow

1. `GameLauncher` allocates an isolated Local Node endpoint, selects `Assets.zip` from the instance, and starts the node before patching or launching the game
2. The node creates one ephemeral Ed25519 key pair for the selected local profile
3. The launcher obtains identity and session tokens from `POST /v1/sessions`
4. `ClientPatcher` redirects known Hytale service prefixes to the loopback authority
5. The game receives scoped certificate trust through `SSL_CERT_FILE` and a Java PKCS#12 trust store
6. DualAuth validates the embedded JWK and handles remote server handshakes without asking the remote server to contact the player's loopback node
7. After the game starts, the launcher transfers Local Node lifetime ownership to the game PID
8. The node remains available if the launcher closes and stops itself when the game process exits

The client patch supports both regular length-prefixed strings and Linux NativeAOT frozen strings where the final character borders runtime metadata. Frozen replacements preserve that metadata byte. The patch can switch between connected and autonomous targets, and HyPrism restores the stable original backup before applying a different target. On macOS, backup and patch state files are stored outside a recognized app bundle to preserve its code signature. Binaries outside an app bundle keep these files beside the binary, and legacy bundle cleanup does not remove active adjacent state files

## Endpoint groups

| Group | Routes |
| --- | --- |
| Readiness and keys | `/health`, `/.well-known/jwks.json`, `/jwks.json` |
| Sessions | `/v1/sessions`, `/game-session`, `/game-session/new`, `/game-session/child`, `/game-session/refresh`, `/game-session/authorize`, `/server-join/auth-grant`, `/server-join/auth-token`, `/game-session/exchange`, `/validate`, `/server/auto-auth` |
| Lifecycle control | `/_hyprism/v1/lifecycle/attach`, `/_hyprism/v1/lifecycle/stop` with the per-process launcher secret |
| Mesh friendship control | `/_hyprism/v1/mesh/profiles/{profileId}/identity`, `/friends`, `/invites`, `/accept`, `/complete`, `/presence` with the per-process launcher secret |
| Real-time gateway | authenticated `/ws` with `peer.session.open`, `peer.send`, and `peer.session.close` bridged through Mesh |
| World invitations | `/world-invite`, `/world-invites`, `/world-invites/sent`, `/world-invites/accept`, `/world-invites/reject`, `/world-invites/cancel`, and `/presence/join-world` |
| Account data | `/my-account/game-profile`, `/my-account/get-profiles`, `/my-account/get-launcher-data`, `/profile/uuid/{uuid}`, `/profile/username/{username}` |
| Avatars and cosmetics | `/my-account/skin`, `/my-account/cosmetics`, `/account-data/skin/{uuid}`, `/player-skins`, `/player-skins/active`, `/player-skins/{skinId}` |
| Compatibility | configs, live config, telemetry, mesh-backed friend, friend-request, presence, and world-invite states, empty party states, presence settings, and empty server listings |

Live config uses the production client's two-step contract. `/configs/...` returns the social feature flags together with an absolute `manifest_url`, the manifest selects a hashed `feature-flags` document for the generic platform, and that document contains the resolved flag dictionary. Descriptor requests are recorded in the Local Node log so a client fallback to zero feature flags can be diagnosed

Authorization grants and access tokens contain the public embedded JWK but never its private `d` value. Access tokens copy the requested certificate fingerprint into `cnf.x5t#S256`. JWKS contains public keys for active sessions only

Child-session and refresh calls issue fresh token pairs with the existing profile key. During `/game-session/authorize`, the Bearer token proves the player's session while the identity token in the request body identifies the target server. This matches the upstream singleplayer handshake and prevents a server identity from being mistaken for the player session

Identity tokens, authorization grants, and server access tokens carry the active character payload in the string-valued `skin` claim used by the upstream server. The embedded server reads this claim during player setup, while the account and player-skin endpoints continue to back the menu editor

`/my-account/cosmetics` follows the `sanasol/hytale-auth-server` response shape. The node reads each character creator category from the active instance's `Assets.zip` and returns all installed item IDs as unlocked. It falls back to the small upstream compatibility catalog only when the archive is unavailable or invalid

## Storage and trust

Each autonomous launch stores its runtime state below `LocalNode/Sessions/<session-id>` in the HyPrism application data directory. This prevents control secrets and trust bundles from colliding between concurrently running local sessions. Local profiles, selected skins, and presence preferences remain in the shared `LocalNode/Accounts.json` file, keyed by the stable UUID of the selected launcher profile

The TLS certificate authority is intentionally shared at `LocalNode/Certificate`. It signs the `h.localhost` server certificate, which is valid for the hostname rather than a particular port. Every Local Node endpoint can therefore use the same trusted chain without another system trust prompt

| File | Purpose |
| --- | --- |
| `Accounts.json` | shared local profiles, saved skins, active skin, and presence preferences keyed by launcher-profile UUID |
| `accounts.lock` | short-lived cross-process lock that serializes changes to shared local profiles |
| `Mesh/Identities/<profile-hash>.json` | stable Ed25519 signing and X25519 agreement identity for one autonomous profile |
| `Mesh/Friends.json` | bounded local friend graph, issued invitation hashes, and replay protection state |
| `Mesh/*.lock` | short-lived cross-process locks that serialize shared mesh state changes |
| `hyprism-local-ca.pfx` | shared local certificate authority and private key in `LocalNode/Certificate` |
| `hyprism-local-ca.crt` | shared PEM public certificate authority in `LocalNode/Certificate` |
| `h.localhost.pfx` | shared server TLS certificate and private key signed by the local authority |
| `h.localhost.crt` | shared PEM server certificate signed by the local authority |
| `client-ca-bundle.pem` | Unix CA bundle inherited by the game process |
| `client-trust.p12` | Java trust store inherited by embedded server JVMs |
| `macos-trusted-v2.crt` | copy of the certificate registered in macOS trust settings, used to skip re-approval on later launches |
The `h.localhost` server certificate rotates when it is invalid, has the wrong host, is not signed by HyPrism's local certificate authority, or has fewer than seven valid days remaining. The certificate authority persists for ten years unless it is invalid. Windows adds that authority to the current user's root store only when its thumbprint is absent, then removes older self-signed HyPrism roots after the active authority is trusted. The Windows server key is imported without `EphemeralKeySet`, which Schannel requires for Kestrel TLS, and without `PersistKeySet`, so the imported key container is released with the certificate. Linux and macOS pass a combined CA bundle to the game process for OpenSSL consumers, and Java receives a dedicated PKCS#12 trust store on every platform

On macOS, the first autonomous launch registers the HyPrism local certificate authority in the macOS admin trust settings so the game client and system TLS consumers trust the loopback endpoint. Registration may show a one-time approval prompt. The `macos-trusted-v2.crt` marker records the registered authority so later launches skip the prompt, and the previous root trust entry is removed only when the authority rotates. The server certificate remains restricted to the `h.localhost` hostname. HyPrism verifies the full chain before launching the game. Canceling the macOS security prompt stops the autonomous launch with an actionable error instead of weakening certificate validation

ASP.NET logging providers are disabled for the companion process, so server request diagnostics do not share the static HyPrism logger or its console stream. The launcher reports only process startup, readiness, attachment, and exceptional control failures. Detailed node events stay in `Logs/<launch-time>/local-node-<port>.log`, and the previous file after size-based rotation is named `local-node-<port>.previous.log`. Unknown request metadata uses `local-node-requests-<port>.ndjson` in the same directory. Authentication routes record only method, path, response status, and duration without headers, tokens, or request bodies

The embedded host receives the active game directory plus shared certificate, account, mesh, and session-log paths automatically. When running `HyPrism.LocalNode` as a standalone process, pass `--assets-path /absolute/path/to/Assets.zip` to expose the complete installed cosmetics catalog, `--certificate-directory /absolute/path/to/Certificate` to reuse an existing trusted local certificate authority, and `--account-data-directory /absolute/path/to/LocalNode` to reuse local profiles, skins, mesh identities, and friendships. Use `--log-file /absolute/path/to/local-node.log` and `--request-journal /absolute/path/to/requests.ndjson` to override the two diagnostic destinations. Without these overrides, standalone mode keeps both files below its data directory

## Mesh friendship foundation

Each autonomous profile receives a persistent mesh Peer ID derived from a dedicated Ed25519 signing key plus a separate X25519 agreement key. This identity is separate from the ephemeral OmniAuth key used for one game process, so friendships survive game and launcher restarts. Version 1 identity files keep their existing Peer ID while receiving an agreement key through an atomic version 2 migration. Private identity files and friend state use owner-only permissions on Unix and inherited current-user application-data permissions on Windows

The manual control API keeps an out-of-band, two-step pairing exchange. The inviter creates a signed `hyprism://friend/v2/invite/` capability with 256 bits of randomness and a lifetime of at most 24 hours. The recipient validates the signature, both public keys, Peer ID, timestamps, size, and one-time capability before returning a signed `hyprism://friend/v2/accept/` response. The inviter completes the exchange only when that response matches an active locally issued capability. The in-game Friend ID flow described below transports the same signed capability automatically. Friendship records created by version 1 pairing have no authenticated agreement key and must be paired again before encrypted transport is allowed

The local state bounds friends, active invitations, consumed invitation hashes, display names, and token sizes. Signed invitation and acceptance payloads also carry the launcher profile UUID required by the Hytale social API. Friendships created before this field was introduced remain valid for mesh encryption but must be paired again before they can appear in the Hytale friend list. Expired replay entries are pruned during mutations, while unexpired entries are never evicted to make room for attacker-controlled input. Friendship control routes remain loopback-only and require the per-process launcher control secret. They never return the private signing key

Confirmed friends derive the same 256-bit pairwise key through X25519 and a context-bound HKDF construction. Mesh envelopes bind sender and recipient Peer IDs, a random message ID, message kind, timestamp, and bounded payload. AES-GCM protects confidentiality and integrity, while Ed25519 adds sender authentication. The inbound pipeline uses a bounded channel with one reader, rejects work before allocation when the queue is full, and maintains a bounded replay window per friend without evicting unexpired entries

Creating an autonomous session activates its mesh profile in the Local Node process. The node sends one personalized encrypted announcement per confirmed friend through IPv4 LAN multicast on `239.255.72.80:47831` and listens for pairwise traffic on an ephemeral UDP port. The public `HPD2` header contains only a one-minute epoch, a 128-bit friend-specific routing tag, a random nonce, and the encrypted payload length. The sender and recipient Peer IDs, timestamp, and transport port stay inside AES-GCM ciphertext authenticated by the sender's Ed25519 signature

Routing tags are derived from the pairwise friendship key, direction, and epoch. Local Node precomputes a bounded lookup index for the current timing window, so an unknown packet is discarded by an opaque tag lookup before signature verification or decryption. Discovery encryption, routing, and regular message envelopes use separate derived keys. Replacing a discovery cycle clears the previous derived key material from memory

Only the intended confirmed friend can recognize and validate an announcement. The advertised endpoint remains a candidate until a correctly signed and encrypted envelope is received from that address, and a fresh replay from another address cannot replace a live authenticated endpoint

Discovery and transport datagrams pass fixed size limits before signature verification or decryption. Discovery packets with unknown opaque routes are discarded before they consume the bounded token bucket, so personalized announcements for large friend lists do not exhaust one another on the receiving node. Known routes and transport datagrams remain rate limited per source IP. Unknown peers, stale announcements, mismatched source endpoints, malformed frames, duplicate message IDs, and full queues are discarded. A valid presence envelope updates the local friend snapshot returned by the protected `/presence` control route. Other authenticated messages enter a separate bounded application queue. Online state expires when signed heartbeats stop, and shutdown sends a best-effort offline presence before closing the sockets

The rotating tags prevent passive LAN observers from reading stable Peer IDs or correlating one tag across epochs. Observers can still estimate the number and timing of active personalized announcements, so this is discovery privacy rather than traffic-flow anonymity

Local Node exposes the Hytale `socket-gateway` envelope at `/ws` and accepts only a valid local session token. The gateway maps `peer.session.open`, `peer.send`, and `peer.session.close` to encrypted `IceSignal` Mesh messages, reports whether the remote profile has a live gateway connection, preserves the peer sequence number and opaque ICE payload, and emits `peer.session.opened`, `peer.message`, `peer.session.closed`, `peer.session.ack`, or `peer.error` back to the client. Message and queue sizes remain bounded, and only a confirmed friend whose signed profile UUID matches the requested player can open a session

World invitations carry the host's opaque P2P invite code in encrypted `WorldInvite` Mesh messages. The receiving node keeps the invitation for ten minutes, exposes it through `/world-invites`, marks its friend as joinable, and forwards received, accepted, rejected, and canceled changes as nested `gateway.notification` events. `/world-invites/accept` and `/presence/join-world` return the P2P invite code in the client's join-response shape. Per-profile invite counts and code sizes are bounded, duplicate datagrams are idempotent, and every lifecycle message is bound to its original friend and both signed profile UUIDs

Players can also pair inside the game dialog without exchanging manual invite codes. Each mesh identity exposes a stable 16-symbol Friend ID computed as a truncated Base32 fingerprint of the Ed25519 public key over a domain-separated SHA-256 hash. The Friend ID carries no address or key material. It is returned as `friendId` by the protected identity control endpoint and written to the Local Node log when the profile activates. Entering it in Hytale's add-friend dialog reaches `/friend-requests/by-username`, where the launcher normalizes confusable characters, rejects malformed input, and starts a pairing request

Because the Friend ID contains no reachable address, each active profile announces its ephemeral UDP transport port in the public Mainline Kademlia DHT under a domain-separated 160-bit topic derived from its own Friend ID. SHA-1 is used only to produce the fixed-size DHT lookup key and provides no authentication. Lookups use standard bencoded `get_peers` queries with compact node and peer values plus announce tokens, and `announce_peer` stores the source UDP port through `implied_port`. Query waves and announce targets are ordered by XOR distance to the topic. A periodic refresh repeats both operations for every active profile while `EnableInternetDiscovery` is on. Public DHT results are restricted to public IPv4 addresses, responses must come from the node that was queried, and all returned endpoints remain untrusted until Mesh identity verification succeeds

Delivering a request first sends a bounded `HPP1` probe to every endpoint returned for the target Friend ID and to the LAN discovery targets. The receiver first returns a stateless HMAC cookie bound to the apparent source endpoint, and only an endpoint that echoes this challenge receives a signed identity response. Only a node that returns a valid short-lived PeerRecord signed by the requested identity receives the full `hyprism://friend/v2/invite/` capability. Both the PeerRecord purpose and request ID are covered by its signature, while the invitation itself is signed and bound to the recipient Friend ID. The receiver then exposes it at `/friend-requests/incoming`. Punch datagrams exchanged through the DHT endpoints let both nodes open NAT mappings toward each other, and acceptance returns as a signed `hyprism://friend/v2/accept/` response over the same path with bounded retransmission. Pairing datagrams pass the same size limits and per-IP token bucket as every other inbound packet, and completion still requires a locally issued capability plus a matching Friend ID fingerprint, so a DHT result cannot impersonate the requested identity

This transport does not yet provide durable mailbox storage, relay traffic, TURN for game traffic, or guaranteed NAT traversal. Hole punching succeeds only for compatible address mappings, so symmetric NATs still need port forwarding, IPv6, UPnP, a VPN, or a later relay layer. DHT nodes learn only the Friend ID topic, the announcing endpoint, and standard bencoded routing fields. Pairing probes contain the target Friend ID, and pre-friend PeerRecords and invitation capabilities are signed but not encrypted, so an active relay on the direct path can observe profile UUIDs, names, and public identity keys. All traffic after friendship confirmation uses the encrypted pairwise Mesh channel

## Limits

Local Node now provides private authenticated discovery, presence, world invitations, join metadata, a peer-session signaling path, and serverless friend requests driven by Friend IDs. Discovery spans one reachable IPv4 LAN plus the public Mainline Kademlia DHT rendezvous while internet discovery is enabled. The full invite lifecycle, gateway path, DHT packet handling, and the Friend ID pairing flow are covered by two-node integration tests, but they have not yet been verified with two installed production Hytale clients behind real NATs. Relay fallback, offline mailbox delivery, TURN for game traffic, and durable state synchronization still require later mesh layers

Mesh activation and persisted-state failures are logged and degrade the social lists to an empty state without preventing creation of the autonomous game session

The HTTP endpoint shapes are based on the open `sanasol/hytale-auth-server` compatibility surface. Gateway and world-invite type names, routes, and payload fields are reconstructed from the installed pre-release client metadata. Automated tests cover the local HTTPS session, account, JWKS, grant exchange, certificate binding, avatar persistence, client patch transitions, encrypted peer-session forwarding, the invitation lifecycle, the built-in Friend ID pairing cycle, and DHT get_peers and announce_peer packet handling. End-to-end verification against every future proprietary Hytale client build still requires a compatible installed client

## Concurrent launches

HyPrism treats each game instance as a separate launch target. A single instance cannot be started twice, because its client files and user data are shared, but different instance directories can run with different authentication modes at the same time. For example, one instance can use Local Node, another a custom authentication service, and a third official authentication

The launcher keeps a runtime process registry with the PID, process start time, instance, and profile. When HyPrism starts again after it was closed, it restores only entries whose process is still alive and whose start time still matches. Entries that ended while the launcher was unavailable are reconciled once so play time and launch cleanup are retained, while stale entries and reused PIDs are removed automatically

Official authentication is deliberately restricted to one running client per Hytale account owner. HyPrism serializes official authentication between launcher processes and refuses a second launch when the restored process registry already contains that account
